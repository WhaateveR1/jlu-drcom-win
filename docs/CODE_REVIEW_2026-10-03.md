## 结论

目前适合作为已验证环境中的个人工具使用，但还不适合作为可以放心分发、长期无人值守的成熟客户端。建议进行范围明确的核心重构：保留 Go、协议构包与校验算法、现有包边界，重构 UDP 请求与回复匹配、会话生命周期、网络配置刷新和错误分类。无须整体推翻，也无须先引入 Windows Service、浏览器 UI 或复杂框架。

这次发现涉及原始代码，也涉及上一轮新增功能。不能用当前能登录或已有测试通过，推导出异常路径已可靠。

## 优先级和证据

- P1：下一轮发布前优先修复，涉及错误的认证状态或用户文件删除。
- P2：影响可靠性、故障恢复、凭据保密或常见部署环境。
- P3：边界配置与维护性问题，可以排在上述问题之后。
- “已复现”指隔离测试直接证明；“静态确认”指代码路径明确，但未对真实系统执行破坏性或断联测试。

### F01 / P1：错误类型的心跳回复仍被当成成功

位置：`internal/protocol/heartbeat.go:21`、`:45`、`:53`；同类问题还存在于 `internal/protocol/logout.go:30`。

KeepAlive 和普通心跳只检查非空，step1 只检查至少 20 字节，随后直接更新 token。服务器的失败通知、旧报文或其他类型的报文，都可能被误记为成功。上一轮修复了登录回复的 `0x04` 检查，但没有修复这些解析器。

已复现：让模拟服务器对一轮全部四次心跳交互都返回以 `0x05` 开头的 40 字节报文，`HeartbeatOnce` 返回成功，状态仍是 `Online`，计数增长到 3。

建议：用脱敏实网报文确认合法应答变体，再验证类型、最小长度和有意义的阶段/序号字段；拒绝错误回复，校验完成后才更新会话。不要仅凭通用 Dr.COM 文档猜测学校服务器的全部应答格式。

### F02 / P1：构建脚本删除运行目录中的用户配置

位置：`scripts/build.ps1:47`。

脚本遍历 `dist/jlu-drcom-win`，删除发布清单外的一切普通文件，其中包括用户按使用指南创建的 `config.toml`、日志及其他本地文件。发布包排除密码配置，不等于允许删除本地运行配置。

已复现：在隔离目录放置虚构账号配置，执行构建脚本后 `config.toml` 消失。

建议：仅在全新 staging 目录组装白名单发布包；刷新已有运行目录时只替换本次生成的受管文件，绝不清理未知用户文件。

### F03 / P2：UDP 没有事务匹配，重复回复导致错误重连

位置：`internal/transport/udp.go:46`、`internal/runner/runner.go:85`、`:108`。

每次 Exchange 发送后只读一个包，检查来源地址就直接返回，未匹配当前请求的应答。UDP 超时重发本身就可能产生迟到或重复回复。登录和 challenge 的解析又位于重试闭包外，导致不匹配报文直接结束该次登录，而不是继续等待正确回复。

已复现：模拟服务器连续发送两份合法 challenge 回复，再正常回应 login。第二份 challenge 被当成 login 回复，报错 `login response too short: got 8 bytes`，虽然正确登录回复随后已经到达。

建议：由单一收包者在总 deadline 内筛选来源及当前阶段匹配的报文，明确处理迟到、重复和服务器异步通知。不要简单清空整个接收队列，以免丢掉有效回复。

### F04 / P2：调试日志泄露密码派生值和会话令牌

位置：`internal/runner/runner.go:312`、`:116`；`cmd/drcom-win/main.go:49`。

登录请求部分字段做了脱敏，但 keepalive 请求通过 `nil` redactions 输出完整数据，其中 `[1:17)` 是密码派生 MD5，`[20:36)` 是服务器令牌。challenge 回复也会输出 salt。`-login-only` 默认日志还直接输出服务器令牌。没有输出明文密码不代表日志不包含凭据材料。

已复现：使用完全虚构的 session，开启 debug 后能在日志中找到未脱敏 MD5 字节。风险是日志被分享、上传或被其他用户读取后暴露认证材料；没有据此声称服务器一定允许会话重放。

建议：集中定义各类报文的敏感字段并测试；默认日志只记录类型、长度、耗时和结果。明文配置是已有明确说明的限制，可后续提供 Windows Credential Manager/DPAPI 存储，但应优先关闭日志泄露。

### F05 / P2：测试失败后，构建脚本仍报告成功并生成发布包

位置：`scripts/build.ps1:19`。

`$ErrorActionPreference = 'Stop'` 本身不能在默认 Windows PowerShell 中把原生命令的非零退出码变成终止异常。脚本没有逐条检查 `$LASTEXITCODE`，因此测试或编译失败后仍可能继续打包。

已复现：隔离副本的 6 项审查测试失败后，脚本仍返回退出码 0，生成 zip，并打印 Packed。当前 GitHub workflow 有单独的 Test 步骤，能阻止那一步的测试失败；这不修复独立构建脚本的行为，也不覆盖后续 build 命令失败。

建议：每条 Go 命令之后立即检查退出码；完成测试、编译和产物验证后再替换正式 zip，失败保留上一次可用产物。相关行为见 [PowerShell 原生命令错误处理文档](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_error_handling)。

### F06 / P2：取消和超时没有传递到正在进行的网络 I/O

位置：`internal/transport/retry.go:14`、`internal/transport/udp.go:51`。

context 只在两次尝试之间检查。一次 `ReadFromUDP` 已经开始后，即使用户点退出或 deadline 已到，也要等固定 ReceiveTimeout。没有写 deadline。默认值下通常表现为退出延迟；用户增大超时后问题更明显。

已复现：context 限制 30ms、socket 超时 400ms，调用仍耗时约 400ms。

建议：Exchange 接收 context，总 deadline 取 context 与配置超时的较早者；取消时唤醒当前读写。正常下线使用独立且严格有界的清理 context。

### F07 / P2：重连沿用旧网卡快照，CLI 与托盘恢复行为不同

位置：`cmd/drcom-win/main.go:23`、`:32`；`internal/runner/runner.go:208`；`internal/trayapp/app_windows.go:359`。

CLI 只加载一次配置，重连工厂闭包始终使用旧 IP/MAC；网络切换或 DHCP 换地址后，重开 socket 不等于重新识别网络。托盘通过外层循环最终会重新加载，但内部 runner 要先耗尽一轮使用旧配置的重连。错误处理分布在两个层次，同一核心的两种入口行为不一致。

静态确认。没有为本次审查切换真实网卡或 DHCP。

建议：把网络快照重新获取、socket 重建和 session 重置归同一个 supervisor 管理，CLI 与托盘复用；凭据配置与运行时网络快照分开。

### F08 / P2：手动 IP 与自动 MAC 可以来自不同网卡

位置：`internal/config/config.go:89`。

当只手动指定 IP、MAC 保持 auto 时，自动探测并不以该 IP 为条件，可能取另一张网卡的 MAC。配置校验仍通过，最终上报的 IP/MAC 组合不一致。

已复现：配置 IP 为 `192.168.1.100`，探测器返回 `10.0.0.1` 所属网卡，解析结果静默组合前者的 IP 和后者的 MAC。

建议：手动 IP 时通过地址查找所属网卡再填 MAC；无法找到时明确报错。全自动选卡也应依据到认证服务器的路由及物理网卡信息，而非只依据名称关键字和枚举顺序。

### F09 / P2：Windows 注销/关机没有下线处理

位置：`internal/trayapp/app_windows.go:532`。

窗口过程处理了手动关闭和销毁，但没有处理 `WM_QUERYENDSESSION`、`WM_ENDSESSION`。Windows 结束用户会话并不保证走菜单 Exit/WM_CLOSE 路径，因而正常关机时不能依赖现有代码发送下线报文。

静态确认；未实际注销当前用户或重启系统。服务端残留会话是否导致下次登录受限，取决于校园网策略，尚未验证。Windows 消息契约见 [WM_QUERYENDSESSION](https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-queryendsession)。

建议：实现有时间上限的会话结束处理，区分取消关机与确认结束，避免无限等待阻碍系统关机；结合睡眠/恢复事件测试会话重建。

### F10 / P2：新增文件日志会让只读安装目录中的程序直接退出

位置：`cmd/drcom-tray/main.go:32`。

这是上一轮新增功能的缺陷。日志固定写在 exe 旁边，创建或打开失败就退出；放在 Program Files 等普通用户不可写的目录时，认证及自启管理均无法运行。GUI 构建主要把错误写到不可见的 stderr，用户可能只看到程序没有启动。

静态确认。当前 D 盘目录可写，故本机未触发。

建议：日志放入当前用户 LocalAppData，打开失败时提供可见错误或可用 fallback；日志轮转应在运行中限制大小，不只在下次启动时检查。获取单实例锁应早于轮转文件，避免第二次启动改动第一进程的日志。

### F11 / P3：配置数值可以溢出为负的时间间隔

位置：`internal/config/config.go:157`、`:298`；`internal/runner/runner.go:133`。

原始整数只验证大于零，转换为纳秒的 `time.Duration` 后没有检查溢出。

已复现：`heartbeat_interval_seconds = 9223372037` 被接受，结果是负的 duration；进入 `time.NewTicker` 会 panic。该问题需要异常的本地配置，不是来自远程报文。

建议：对超时、心跳间隔和重试次数给出合理上下界，在转换前防溢出。自制 TOML 解析器还会静默接受未知键和重复键，应采用成熟解析器并校验未知字段。

## 验证与覆盖局限

原有测试全部通过，`go vet ./...` 通过，使用本机 GCC 开启 CGO 后 `go test -race ./...` 也通过。race 通过仅意味着已执行路径未发现数据竞争，并不能覆盖没有执行的托盘消息/启动管理交互。

当前覆盖率：protocol 92.7%，runner 69.2%，config 62.3%，transport 42.3%，trayapp 8.0%；CLI、托盘入口及 logging 为 0%。高协议覆盖率仍未发现任意心跳被接受，说明测试断言和测试场景比覆盖率数字更关键。部分测试会调用同一个 Checksum 实现计算预期值，缺少独立的完整报文基准。

审查使用本机仓库外的 `audit-work` 隔离副本，只复制源码和公共模板，不含真实账号配置。新增 6 项 TestAudit 测试全部失败，分别证明 F01、F03、F04、F06、F08、F11。另一次独立构建测试证明 F02、F05。构建测试只删除了人工放入的虚构配置；隔离脚本添加了清理路径边界断言，不改变受审的构建和配置清理逻辑。

复现命令：

```powershell
# 在审查时的隔离副本内运行（不属于正式仓库）
go test ./internal/runner ./internal/transport ./internal/config -run TestAudit -v -count=1
```

这些失败测试故意留在隔离副本，未加入正式源码测试集，后续修复时可以逐项转入正式回归测试。隔离目录的构建产物仅用于审查，不能替换当前运行版本。

本次没有执行真实错误密码登录、账号锁定测试、系统关机、睡眠、拔网线或校园服务器畸形应答测试。没有把这些未验证情况写成已发生的故障。

## 重构建议与验收顺序

1. **先修可独立验证的问题。** 修复发布脚本退出码和用户文件保护、日志脱敏及日志存储目录。补对应回归测试；保持已验证的协议构包不变。
2. **统一会话管理。** 用一个供 CLI/托盘复用的 supervisor 管理登录、心跳、重连、网络快照和停止。区分永久配置/凭据错误与瞬时网络错误，明确何时等待用户修正、何时自动重试，并对连续故障退避。
3. **重构收包与校验。** 建立 context 感知的请求/应答匹配，使用脱敏的校园实网报文作为独立测试基准，覆盖丢包、重复、乱序、截断、错误源地址和异步消息。协议构包继续保持纯函数，不增加 DNS 或系统路由副作用。
4. **补齐 Windows 集成。** 托盘只负责展示和命令，处理会话结束及恢复事件；以可替换接口封装计划任务和网卡 API。测试无网开机、账号配置错误、重复启动、Explorer 重启、睡眠恢复、多网卡、只读安装目录，以及 TUN 开关状态。

接受标准应包括：当前异常测试逐项转绿；原有测试和 race/vet 通过；发布过程失败时不产生“成功”包且不改用户配置；保持相同凭据与已验证协议字段的实网登录/双心跳/下线；断联测试具有独立本地恢复保障。日志和托盘明确区分已认证、网络待恢复、配置错误与网站探测结果。

无需为了“现代化”而把 Go 换成其他语言，也不应把协议要求的 MD5 擅自改成 SHA-256。网络认证、系统 DNS 和 Clash 管理应继续分开，避免客户端运行时自动修改整机代理或 DNS。
