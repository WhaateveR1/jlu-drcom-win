# 校园网、Clash 与 DNS 排查

## 三种不同的状态

- `Authenticated`：认证服务器返回成功回复，客户端继续发送心跳。
- DNS 可用：系统配置的 DNS 能把域名解析为可用地址。
- 网页可用：域名解析、直连或代理线路、TLS 和网站服务均正常。

认证报文里的 `primary_dns` 不会修改 Windows 的网卡 DNS。修改此配置字段不能修复系统 DNS 配置。

## 关闭 TUN 后打不开网页

2026-10-03 在实际校园网环境中验证：物理网卡固定使用 `8.8.8.8`，关闭 TUN 后该 DNS 不回应；`10.10.10.10`、`10.10.10.11` 均能回应。把物理网卡 DNS 改为这两个校园 DNS 并清除缓存后，在 TUN 与系统代理均关闭时，百度和吉林大学官网均返回 HTTP 200。恢复 TUN 后两站也均返回 HTTP 200。

此前用指定 DNS 得到地址后的探测仍失败，不能单独据此认定认证失效：Clash fake-IP 的系统缓存可能影响探测。应清除 DNS 缓存、记录实际解析地址，并确认整个探测期间 TUN 状态没有被恢复进程改变。

可先只读查看配置：

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4
Get-NetUDPEndpoint -LocalPort 61440
Get-Content "$env:LOCALAPPDATA\jlu-drcom-win\logs\tray.log" -Tail 30
```

仓库中的 `scripts/Set-CampusDns.ps1` 只在明确执行时修改指定网卡，要求管理员权限，并验证网卡 GUID、备份原 DNS。正常认证过程不会自动修改 DNS、Clash 配置或全局路由。不同校园网络应先验证当地 DNS。

## 不运行认证客户端时，代理可用而直连不可用

Clash 规则可以让一部分网站经过代理、一部分直接访问。代理线路能连接不等于校园网直连已完成认证；停止客户端后的剩余认证会话也可能暂时有效。因此这组现象不能单独证明认证成功或客户端破坏了路由。需要对照同一个网站、实际命中的规则和客户端日志判断。

## 开机启动

旧版使用注册表 Run 项，Windows 可以推迟启动这类程序。新版使用当前用户登录计划任务，无人为延迟，带 `-autologin`；网卡未就绪或瞬时网络失败时按 5、10、20、40、60 秒退避重试。配置错误或登录被拒绝时暂停，修正后点击 Login。客户端按当前用户权限运行，没有 Windows Service，也不保证在登录桌面之前完成认证。

迁移结果可通过 `Get-ScheduledTask` 和日志检查。实际启动耗时必须在下一次登录后确认，不能用一次手动启动代替开机测试。

## 远程排查保障

如果当前协作会话依赖 Clash，不要直接关闭 Clash 进程。优先用绑定物理接口的单独探测连接。在必须关闭 TUN 时，应先启动独立的本地恢复进程，并验证它已就绪；主测试还应使用 `finally` 恢复 TUN。即使会话中断，独立进程仍须能恢复原网络状态。
